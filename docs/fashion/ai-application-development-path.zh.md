# AI 应用开发思考与个人技术路线

[English](ai-application-development-path.md) | 中文

本页是项目作品的延伸阅读。招聘者应先通过 [Fashion Harness 项目首页](../../README.zh.md)、[工程验证证据](validation-and-evidence.zh.md)和[贡献与关键代码地图](contribution-and-ownership.zh.md)判断作品本身；以下内容再说明我如何形成项目、如何理解 AI 应用开发，以及准备继续补强什么。个人思考用于解释可持续的工作方法，不替代已经实现的功能和验证证据。

## 1. 职业定位

我的近期主攻方向是 AI 应用开发、Agent／Harness 应用工程，以及重视行业理解和现场交付的 FDE／AI 解决方案岗位。相邻方向包括 AI 应用后端、Agent 评测和测试开发；长期希望继续进入 Agent Infra、模型推理与系统工程。

选择这些方向的原因，是我更擅长把一个模糊行业问题逐步转成产品范围、领域对象、任务规格、AI 协作实现、测试验收和后续迭代。Fashion Harness 是当前最完整的公开证据，其他规划只有在形成代码、测试、实验或可复核交付后，才会进入正式作品和简历。

## 2. 我对 AI 应用开发的理解

AI 应用开发不只是接入模型接口。一个能够进入真实工作的 AI 应用，需要同时组织以下部分：

| 组成 | 我关注的问题 |
| --- | --- |
| 业务场景（Domain） | 用户真正需要完成什么任务，哪些判断必须保留给专业人员 |
| 数据与证据（Data / Evidence） | 信息来自哪里，哪些是事实、推导或仍待验证内容 |
| 模型与上下文（Model / Context） | 模型看到什么信息，输出能支持什么结论，何时需要更换模型或策略 |
| 工具与权限（Tool / Permission） | Agent 可以读取或修改什么，如何限制越权和跨项目访问 |
| 工作流与状态（Workflow / State） | 如何保存中间结果、版本、审核、失败和恢复状态 |
| 人工决策（Human-in-the-loop） | 人在哪些节点比较、修改、批准、拒绝并承担最终责任 |
| 工程验证（Engineering Validation） | 如何通过测试、启动、浏览器流程和版本证据确认当前实现 |
| 反馈与迭代（Feedback / Iteration） | 如何把真实使用问题转成下一版规则、交互和验收标准 |

Fashion Harness 将这些问题放进服装研究与设计决策场景中：AI 负责整理证据和提出候选，人负责专业判断、审核和批准，项目记录负责保留事实、版本和评测依据。

## 3. 我的项目工作方法

**理解行业任务与真实限制**（Problem Discovery）<br>
↓<br>
**定义范围、业务对象与人工责任**（Scope / Domain Model / Human Authority）<br>
↓<br>
**冻结任务规格与验收标准**（Specification / Acceptance Criteria）<br>
↓<br>
**组织 AI 工具完成实现、调查与复核**（AI-assisted Implementation / Audit）<br>
↓<br>
**运行测试并完成人工主流程检查**（Test / Human Verification）<br>
↓<br>
**保存版本证据、公开边界和改进项**（Versioned Evidence / Improvement）

在 Fashion Harness 中，这套方法已经对应到领域建模、Cursor 主要实现、Codex 调查与独立验证、项目所有者人工决策、冻结提交和截图证据。具体分工见[开发过程与 AI 协作](development-process.zh.md)。

## 4. 当前形成的个人优势

- **行业问题拆解**：能够把模糊需求拆成用户流程、领域对象、关键规则和阶段范围；
- **产品与系统连接**：能够同时考虑业务价值、人工责任、技术实现、运行条件和长期演进；
- **AI 协作开发**：能够为 Cursor、Codex 等工具划分实现、调查、审计和验证任务，并复核结果；
- **证据化交付**：重视代码、测试、运行、截图、提交和已知限制之间的对应关系；
- **长期规划与阶段落地**：能够把模型、数据、Agent、工程和基础设施规划拆成当前可验证的薄切片；
- **快速学习迁移**：根据真实项目问题学习新技术，并把学习结果转成代码、测试、实验、复盘或面试讲解。

这些优势以当前作品证据为基础。Fashion Harness 尚未覆盖的能力，会在[项目状态与后续方向](roadmap-and-boundaries.zh.md)中保留进入条件，不提前写成完成结果。

## 5. 当前技术实践与成长路线

当前已经通过项目接触并应用 TypeScript、React、领域建模、Controller、状态与版本规则、Vitest、构建配置、Agent 只读工具、浏览器验证和 Git 证据管理。我能够结合项目解释关键对象、数据流、人工审核、权限设计和验证结果，并继续提高独立修改、调试和测试的深度。

近期学习不是把所有语言同时提高到相同深度，而是建立一条独立工程主轴，再根据真实项目扩展横向能力：

| 技术线 | 当前基础与用途 | 下一项可复核进展 |
| --- | --- | --- |
| Python 第一主轴 | 已有 AI 应用、API 调用、RAG／Agent、类型与基础测试实践 | 独立完成包含接口、状态、异常日志和测试的后端或 Agent 垂直切片 |
| 后端工程共享主轴 | 将接口、数据库、配置、异常、日志、测试和部署作为 Python 与 Java 共通能力 | 形成可启动、可调试、可测试并能说明故障处理的服务证据 |
| Java 渐进副主轴 | 已有 OOP、设计模式、数据库与课程实践基础 | 通过 Spring Boot、JUnit 和数据库完成一个边界清楚的工程闭环，不强行接入 Fashion Harness |
| TypeScript／React 项目驱动线 | 已在 Fashion Harness 中阅读、审查和验证相关实现 | 围绕真实缺口完成受控修改、客户端测试和调试记录 |
| Agent／Harness 深化线 | 已能结合项目说明领域对象、只读上下文、权限和人工审核 | 补充 Runtime、Tool 权限、状态恢复、失败测试和可观测性证据 |

长期路线由五层组成，并通过真实项目逐步汇合：

1. **基础设施层**：操作系统、网络、存储、容器、GPU、RAM 与 SSD；
2. **模型层**：LLM／VLM、推理、量化、训练、模型路由与评测；
3. **AI 系统层**：Harness、Agent、Memory、RAG、Tool、Sandbox 与任务恢复；
4. **工程层**：Python 主轴、多语言工程、API、数据库、并发、测试与部署；
5. **产品与 FDE 层**：需求拆解、技术选型、行业适配、可靠性、成本和交付。

这五层不是一次性学习清单。优先级来自目标岗位的真实要求和项目中反复出现的缺口，每项学习都需要形成可复核产物。

## 6. 对行业与岗位的个人判断

基于个人参加开发岗位面试、阅读岗位要求和推进项目的经历，我观察到很多团队仍然高度重视编码基础、系统可靠性、安全性和可控交付；同时，能够把模型能力接入具体业务流程、设计权限与人工节点、验证输出并持续改进，也是 AI 应用岗位的重要价值。

因此，我的路线不是放弃传统工程基础，而是在持续加强独立编码、调试、测试和后端能力的同时，重点发展 AI 应用设计、Agent 工作流、行业问题理解和人机协作交付。投递时优先选择以下团队：

- 以 AI 应用、Agent 或模型能力产品化为核心的公司与团队；
- 正在进行明确 AI 转型，并具有工程验证与安全机制的大型企业；
- 在垂直行业中有真实业务场景、数据边界和交付责任的 AI 产品团队。

具体公司和岗位仍以最新职位描述、实际团队职责和面试沟通为准，不用公司规模或岗位名称替代真实匹配判断。

## 7. 求职材料如何使用本页

简历只保留一句定位和一条作品入口：

> 面向 AI 应用开发与 Agent 工程，具备行业问题拆解、系统规划、AI 协作开发、测试验收和持续迭代实践；可通过 Fashion Harness 作品与版本化证据进一步查看。

GitHub 项目首页负责展示产品与工程结果，本页负责解释项目背后的个人方法和长期路线；面试时再结合目标岗位选择一个设计决策、一次验收修复或一个后续改进方向深入说明。内部长期规划、受访者原始材料和未经核验的设想不会直接作为公开能力证明。
