# 开发过程与 AI 协作

[English](development-process.md) | 中文

## 1. 工作方式

项目采用“规划—规则—实现—验证—复盘”的迭代方式，将每次 AI 协作放入明确的任务、验收和版本记录中。

**定义产品问题与范围**（Problem / Scope）<br>
↓<br>
**冻结领域规则与验收标准**（Specification / Acceptance Criteria）<br>
↓<br>
**Cursor 完成主要代码与测试实现**（Implementation）<br>
↓<br>
**Codex 调查、审计并设计验证**（Research / Audit / Validation Design）<br>
↓<br>
**项目所有者复核并决定是否接受**（Human Review / Decision）<br>
↓<br>
**运行验证并保存版本证据**（Verification / Versioned Evidence）

每轮工作的具体内容包括：

1. **需求和范围**：先明确用户任务、当前工程切片、长期愿景与不做事项；
2. **领域建模**：把来源、证据、机会、概念、审核、反馈和评估建成可测试对象；
3. **规则设计**：把三方向、版本绑定、批准失效和交付条件写成不变量；
4. **AI 辅助实现**：使用 Cursor 完成主要代码与测试实现；
5. **独立审计**：使用 Codex 调查现状、复核差异、规划公开化调整并检查证据；
6. **人工决策**：由项目所有者决定产品目标、规则、边界、技术路线和是否接受结果；
7. **验证与留痕**：分别记录已完成检查、保留问题和证据适用范围，再决定公开内容。

## 2. 贡献说明

| 参与方 | 主要职责 | 本项目中的可见产出 |
| --- | --- | --- |
| 项目所有者 | 产品问题定义、系统规划、领域规则、任务组织、范围取舍、技术路线、验收标准、复核决策与最终责任 | 工作流、关键不变量、任务规格、验收结论、公开范围和迭代方向 |
| Cursor | 根据冻结规格完成主要 Fashion 代码与测试实现，并按复核结论执行工程调整 | 领域包、Controller、Fashion Shell、Bundle、定向测试和修复提交 |
| Codex | 资料调查、状态审计、风险分析、任务拆分、验收设计、独立验证和公开材料校正 | 差异与风险清单、验证方案、复核结论、证据文档和招聘者阅读路径 |

这种分工体现的是 AI 应用开发中的组织与交付能力：项目所有者能够理解需求、设计系统与规则、把任务交给合适工具执行、检查结果、修正偏差并对最终交付负责。源码作者与保留的上游归属则通过提交历史和[贡献、归属与关键代码地图](contribution-and-ownership.zh.md)明确说明。

## 3. AI 输出复核机制

- 关键业务行为使用领域不变量和测试约束；
- AI 生成的改动与任务清单、验收标准和代码差异逐项核对；
- 审计角色与主要实现角色分离；
- 测试数字只引用实际运行结果，并注明对应阶段；
- 待运行检查保留为待验证状态，完成后使用绑定冻结提交的实际证据更新；
- 技术经历按实际参与深度说明，并连接到能够解释、修改或验证的项目内容；
- 合成演示数据、工程验证、真实访谈和产品试用分别记录，保持证据类型清晰。

## 5. 形成的可复用工作方法

该过程形成了以下可以迁移到其他 AI 应用项目的工作方法：

- 从模糊场景形成可实施范围；
- 将业务判断转成对象、状态与不变量；
- 让 Agent 在受控上下文和权限边界内工作；
- 协调多个 AI 工具承担实现、审计和材料整理的不同角色；
- 通过测试、静态校验、浏览器证据和版本记录建立交付可信度；
- 将技术缺口反馈到后续学习与开发路线。
