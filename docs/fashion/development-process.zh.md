# 开发过程与责任边界

[English](development-process.md) | 中文

## 1. 工作方式

这个项目采用“规划—规则—实现—验证—复盘”的迭代方式，而不是把一次 AI 生成结果直接当成交付物。

1. **需求和范围**：先明确用户任务、当前工程切片、长期愿景与不做事项；
2. **领域建模**：把来源、证据、机会、概念、审核、反馈和评估建成可测试对象；
3. **规则设计**：把三方向、版本绑定、批准失效和交付条件写成不变量；
4. **AI 辅助实现**：使用 Cursor 完成主要代码与测试实现；
5. **独立审计**：使用 Codex 调查现状、复核差异、规划公开化调整并检查证据；
6. **人工决策**：由项目所有者决定产品目标、规则、边界、技术路线和是否接受结果；
7. **验证与留痕**：将“已经检查”和“尚未验证”分开记录，再决定能否公开。

## 2. 贡献说明

| 参与方 | 主要职责 |
| --- | --- |
| 项目所有者 | 产品问题定义、系统规划、领域规则、范围取舍、技术路线、验收标准和最终决策 |
| Cursor | 主要代码与测试实现，以及按明确要求进行工程调整 |
| Codex | 资料调查、独立审计、作品集规划、变更复核和公开材料校正 |

这不是“所有代码均由项目所有者独立手写”的作品。项目希望证明的是：项目所有者能够理解需求、设计系统与规则、组织 AI 工具推进工程、检查结果、识别边界并对交付负责。

## 3. 如何避免把 AI 输出当成事实

- 关键业务行为使用领域不变量和测试约束；
- AI 生成的改动需要与任务清单和代码差异逐项核对；
- 审计角色与主要实现角色分离；
- 测试数字只引用实际运行结果，并注明对应阶段；
- 未运行的检查明确标记为待验证，只有绑定冻结提交的实际证据才能替换该状态；
- 不把代码中出现的技术自动等同于项目所有者已经熟练掌握的技能；
- 不以演练数据、种子数据或规划文档冒充真实客户结果。

## 5. 可复用的方法

该过程刻意保留以下可复用能力证据：

- 从模糊场景形成可实施范围；
- 将业务判断转成对象、状态与不变量；
- 让 Agent 在受控上下文和权限边界内工作；
- 协调多个 AI 工具承担实现、审计和材料整理的不同角色；
- 通过测试、静态校验、浏览器证据和版本记录建立交付可信度；
- 将技术缺口反馈到后续学习与开发路线。
