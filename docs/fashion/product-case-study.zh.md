# 产品案例：把生成式输出变成可审核的设计决策

[English](product-case-study.md) | 中文

## 1. 问题定义

通用聊天界面可以快速生成服装灵感，但很难回答几个交付问题：资料来自哪里、结论如何形成、设计方向为何不同、谁批准了当前版本、修改后旧批准是否仍有效，以及最终输出能否被复核。

Fashion Harness 将问题定义为：建立一个可追溯、可人工审核、可迭代的服装研究与设计决策工作台，而不是只生成一段“看起来合理”的回答。

## 2. 当前用户与任务

当前工程切片面向需要把初步 Brief 转换为设计方向的产品策划者或设计师。核心任务是：

1. 建立项目和 Brief；
2. 记录研究任务、来源、样本和证据；
3. 将属性、热度信号和分析运行组织为趋势机会；
4. 从被选定的机会版本生成恰好三个、彼此有区分度的概念；
5. 由人工审核、要求修改或批准；
6. 在版本变化时使旧批准失效；
7. 导出带快照摘要的交付物；
8. 保存反馈、结果可用性和评估记录。

## 3. 产品决策

### 决策一：对象先于界面文案

研究层使用 `ResearchTask`、`Source`、`Sample`、`Evidence`；分析层使用 `AnalysisRun`、`TrendCluster`、`DesignOpportunity`；设计层使用 `ConceptSet`、`ReviewRound`、`DesignDeliverable`。对象化设计让来源、版本和状态可以被测试，而不是散落在对话文本里。

### 决策二：人工判断是主流程，不是异常处理

证据需要人工复核，机会需要显式选择，概念需要审核，修改会触发新的审核状态。系统不把模型输出等同于事实或批准结果。

### 决策三：审批绑定版本

`review_ready` 状态要求概念集恰好包含三个彼此区分的方向；批准只对当前选择和当前版本有效。设计发生变化时，已有批准会被失效，避免旧结论误用于新内容。

### 决策四：结果未知也是有效状态

反馈层以 `OutcomeAvailability` 区分“尚未观察”“不可获得”和“已有数据”，而不是用虚构指标填补空白。当前仓库没有真实销量或商业效果，因此不作相关主张。

## 4. 当前结果

| 能力 | 状态 | 说明 |
| --- | --- | --- |
| 领域对象与状态规则 | Implemented | 分布在七个 Fashion 领域包中 |
| 项目与 Session 绑定 | Implemented | Harness 读取紧凑的项目快照 |
| 只读项目查询工具 | Implemented | 工具只接受 section，projectId 由宿主绑定 |
| 三方向、审核、交付规则 | Implemented | 有对应领域不变量与定向测试 |
| 公开化相关定向检查 | T-04 verified | 60 个定向测试及相关校验通过 |
| 最终应用全量验证 | Pending T-06 | 尚不能声明最终构建和浏览器闭环通过 |
| 真实设计师使用反馈 | Not claimed | 尚无真实用户研究结论 |

## 5. 已知产品缺口

- 分析引用的存在性与归属尚未被系统完整验证；
- 目前没有覆盖所有字段和版本的完整 Brief 修订界面；
- `ImprovementItem` 候选不保证强一致，也不会自动修改业务对象；
- Evaluation 依赖 Git 检出环境；
- 最终全量构建与无密钥浏览器流程尚待 T-06 验证。

这些缺口被保留为明确边界，而不是包装成已完成能力。
