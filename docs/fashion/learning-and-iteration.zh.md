# 学习与迭代

## 1. 边学习边开发的原则

Fashion Harness 不是用代码数量证明“已经掌握所有技术”，而是把真实项目问题映射成学习任务，再把学习结果用于下一轮设计和实现。

每次迭代都回答四个问题：

1. 当前用户任务中最关键的不确定性是什么；
2. 哪个领域规则或工程证据可以降低不确定性；
3. 项目所有者需要补充理解、能够解释和能够修改的内容是什么；
4. 哪些部分仍由 AI 辅助完成，哪些结论尚未验证。

## 3. 技术学习的诚实边界

项目中出现 TypeScript、React、领域建模、测试、Agent 工具和构建配置，不等于项目所有者已经独立熟练掌握所有实现细节。公开表达按以下层次区分：

- **亲自设计与决定**：产品目标、领域划分、关键规则、范围、技术路线和验收标准；
- **能够解释、修改和验证**：通过审阅、测试和迭代已经形成理解的部分；
- **AI 辅助实现**：主要 Fashion 代码和测试由 Cursor 根据冻结规格实现，Codex 参与资料调查、风险分析、验收设计、独立验证与公开材料校正；
- **尚待掌握或实现**：在路线图中明确标为 Planned 或学习目标。

Python 与 Java 学习仍可并行，但不会因为仓库采用了某项技术，就把它自动写成个人已熟练掌握的技能。

## 4. 真实访谈和产品试用如何进入下一轮

当前已经完成首位服装设计师的真实工作场景访谈，用于理解其研究来源、决策流程、必须由人完成的专业判断和二期优化方向。这属于场景研究（Contextual Research），不是一期产品试用（Product Trial），也不能证明可用性或效果。

作品集整理和一期缺口修复完成后，下一轮分两条记录推进：

1. **补充访谈**：补齐首次访谈中未充分回答的问题，继续校准业务流程和专业边界；
2. **产品试用**：让设计师使用一期产品完成任务，单独记录操作摩擦、理解偏差、可用性反馈和修改建议。

试用反馈进入版本迭代的路径为：

**观察实际使用**（Observe）<br>
↓<br>
**记录结构化反馈**（Designer Feedback）<br>
↓<br>
**区分问题类型与证据等级**（Triage / Evidence State）<br>
↓<br>
**调整规则、交互或任务规格**（Rule / Interaction / Specification）<br>
↓<br>
**重新测试与人工验收**（Test / Human Acceptance）<br>
↓<br>
**形成新版本证据**（Versioned Evidence）

仓库中的合成案例只验证产品流程、领域对象和工程衔接，不替代真实访谈或产品试用；未经允许也不公开访谈原始记录和可能识别受访者的信息。

## 5. 面向求职的意义

仓库希望展示的不只是一个功能页面，还包括需求理解、系统设计、技术组合、AI 工具协作、验证交付、边界表达和持续学习能力。任何面试表述都应能回到代码、文档或验证证据，并允许面试官追问“为什么这样设计、如何验证、哪里还没完成”。
