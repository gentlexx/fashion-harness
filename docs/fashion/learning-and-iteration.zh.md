# 学习与迭代

[English](learning-and-iteration.md) | 中文

## 1. 边学习边开发的原则

Fashion Harness 不是用代码数量证明“已经掌握所有技术”，而是把真实项目问题映射成学习任务，再把学习结果用于下一轮设计和实现。

每次迭代都回答四个问题：

1. 当前用户任务中最关键的不确定性是什么；
2. 哪个领域规则或工程证据可以降低不确定性；
3. 项目所有者需要补充理解、能够解释和能够修改的内容是什么；
4. 哪些部分仍由 AI 辅助完成，哪些结论尚未验证。

## 2. 当前能力证据与学习映射

| 项目问题 | 已形成的能力证据 | 后续学习方向 |
| --- | --- | --- |
| 聊天输出难以追溯 | Source、Sample、Evidence 与分析链 | 数据治理、引用完整性、来源授权 |
| 模型输出容易越权 | Session 绑定、只读查询、受控快照 | Agent 权限、工具契约、上下文工程 |
| 设计方向容易同质化 | 三方向与两两区分不变量 | 评价量表、设计语义和人机协作 |
| 修改后审批可能过期 | 版本绑定与批准失效 | 事件模型、状态机与审计日志 |
| AI 实现难以直接信任 | 定向测试、独立审计、阶段门禁 | 测试设计、调试、全链路验证 |
| 规划容易大于实现 | Implemented / Pending / Planned 标签 | 范围管理、交付节奏和技术债治理 |

## 3. 技术学习的诚实边界

项目中出现 TypeScript、React、领域建模、测试、Agent 工具和构建配置，不等于项目所有者已经独立熟练掌握所有实现细节。公开表达按以下层次区分：

- **亲自设计与决定**：产品目标、领域划分、关键规则、范围、技术路线和验收标准；
- **能够解释、修改和验证**：通过审阅、测试和迭代已经形成理解的部分；
- **AI 辅助实现**：主要代码和测试由 Cursor 根据规划实现，Codex参与审计与材料校正；
- **尚待掌握或实现**：在路线图中明确标为 Planned 或学习目标。

Python 与 Java 学习仍可并行，但不会因为仓库采用了某项技术，就把它自动写成个人已熟练掌握的技能。

## 4. 反馈如何进入下一轮

当前系统已经为反馈、结果可用性、开发事件和改进候选预留结构。下一轮迭代计划遵循：

`设计师观察 → 结构化反馈 → 问题分类 → 规则或交互调整 → 测试与评估 → 新版本证据`

在真实设计师测试发生前，只能使用虚构 walkthrough 验证表达和对象衔接，不能把它写成用户验证。

## 5. 面向求职的意义

仓库希望展示的不只是一个功能页面，还包括需求理解、系统设计、技术组合、AI 工具协作、验证交付、边界表达和持续学习能力。任何面试表述都应能回到代码、文档或验证证据，并允许面试官追问“为什么这样设计、如何验证、哪里还没完成”。
