## 1. 边学习边开发的原则

Fashion Harness 将真实项目问题映射成学习任务，再把学习结果用于下一轮设计和实现；代码、测试与验证记录共同展示每项判断如何落地。

每次迭代都回答四个问题：

1. 当前用户任务中最关键的不确定性是什么；
2. 哪个领域规则或工程证据可以降低不确定性；
3. 项目所有者需要补充理解、能够解释和能够修改的内容是什么；
4. 哪些部分仍由 AI 辅助完成，哪些结论尚未验证。

## 3. 当前个人技术情况

通过 Fashion Harness 的产品设计、任务组织、实现协作、代码审阅和验收复核，我已经实际接触 TypeScript、React、领域建模、测试、Agent 工具、构建配置和浏览器验证。不同技术的熟练程度并不完全相同，当前可以按实际参与深度说明：

- **能够主导设计和决策**：产品目标、用户流程、领域划分、关键规则、项目范围、技术路线取舍和验收标准；
- **能够结合项目解释和验证**：说明关键对象、数据流、人工审核规则、Agent 权限、版本约束、测试结果和浏览器主流程，并根据问题定位到相关文档与代码；
- **具备 AI 协作开发经验**：将需求拆成可执行规格，使用 Cursor 完成主要 Fashion 代码和测试实现，使用 Codex 辅助调查、风险分析、验收设计、独立验证与公开材料校正；
- **正在继续深化**：TypeScript／React 实现细节、测试设计、调试、状态机、数据治理、Agent 工具契约和持续集成。

Python 与 Java 仍在并行学习。求职沟通时，我会结合具体项目任务说明各项技术的实际接触深度、能够完成的工作和正在加强的部分。

## 4. 真实访谈和产品试用如何进入下一轮

当前已经完成首位服装设计师的真实工作场景访谈，用于理解其研究来源、决策流程、必须由人完成的专业判断和二期优化方向。这属于场景研究（Contextual Research），不是一期产品试用（Product Trial），也不能证明可用性或效果。

作品集整理和一期缺口修复完成后，下一轮分两条记录推进：

1. **补充访谈**：补齐首次访谈中未充分回答的问题，继续校准业务流程和专业边界；
2. **产品试用**：让设计师使用一期产品完成任务，单独记录操作摩擦、理解偏差、可用性反馈和修改建议。

试用反馈进入版本迭代的路径为：

**观察实际使用**（Observe）<br>
↓<br>
**记录结构化反馈**（Designer Feedback）<br>
↓<br>
**区分问题类型与证据等级**（Triage / Evidence State）<br>
↓<br>
**调整规则、交互或任务规格**（Rule / Interaction / Specification）<br>
↓<br>
**重新测试与人工验收**（Test / Human Acceptance）<br>
↓<br>
**形成新版本证据**（Versioned Evidence）

仓库中的合成案例只验证产品流程、领域对象和工程衔接，不替代真实访谈或产品试用；未经允许也不公开访谈原始记录和可能识别受访者的信息。

## 5. 面向求职的意义

仓库集中展示需求理解、系统设计、技术组合、AI 工具协作、功能实现、验证交付、范围管理和持续改进能力。面试中的项目说明可以回到代码、文档或验证证据，并进一步回答“为什么这样设计、如何验证、下一步如何改进”。
