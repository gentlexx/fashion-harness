# Expected Boundaries

## 这个演练可以说明

- 当前公开文档如何使用代码中的领域名称；
- Brief、研究、分析、设计、审核、交付、反馈和评估之间的预期关系；
- 为什么要恰好三个、彼此区分的设计方向；
- 为什么内容变化后需要重新确认批准；
- 为什么“尚未观察到结果”比虚构商业指标更诚实；
- 为什么改进候选需要人工判断，而不是自动写回业务状态。

## 这个演练不能证明

- 任何真实品牌、市场、趋势、用户或客户结论；
- 真实服装设计师已经使用或认可该产品；
- 真实销量、转化率、预测准确度或商业效果；
- JSON 可以导入当前应用或完全符合内部 schema；
- Agent 已经具备 Fashion 写权限或多 Agent 自主执行能力；
- 最终应用已完成全量构建、测试或浏览器验收；
- 项目所有者独立手写了所有实现代码。

## 需要真实验证的后续步骤

1. T-06 在最终应用提交上完成构建、测试、启动和浏览器主流程；
2. 使用全新本地数据目录验证无历史状态依赖；
3. 不填写或展示真实 API Key，验证无密钥时引导不遮挡 Fashion 主流程；
4. 按最终应用 SHA 采集六张截图；
5. 设计真实的设计师试用任务、知情说明与反馈记录；
6. 将真实观察与虚构样本完全分开保存和表达。
